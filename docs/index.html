Skills as git objects.

git-skill stores your AI agent skills the same way git stores code — as tree objects, versioned with tags, distributed with any git remote, pinned by commit SHA for reproducible installs.

Why git-skill

Skills deserve the same rigor as code.

A skill is a prompt + supporting files that change how an agent behaves. Today they're scattered across folders, gists, and copy-pasted snippets. There's no version, no lockfile, no way to say "every machine in our team runs this exact review skill at this exact SHA". git-skill fixes that, using only the git you already have.

git-native

Every skill is a real git commit pointing at a real git tree under refs/skills/<name>. git log, git diff, git cat-file — they all just work. No new database, no central registry, no SaaS.

Reproducible

skill.lock pins skills to a commit SHA, not a tag. A tag can move; a SHA can't. git skill sync on any machine produces byte-identical files.

Portable

Any git remote that supports pushing refs works — GitHub, GitLab, Bitbucket, Gitea, a bare repo on a USB stick. Public, private, monorepo, polyrepo, doesn't matter.

Cross-platform

Lockfile paths are repo-relative, forward-slash. Symlink targets are relative-to-parent. A skill.lock written on Windows works on Linux and macOS, unchanged.

Single binary

A ~3 MB Go executable. No runtime, no daemon, no shell rewrites. Drop in your PATH and git skill ... works as a git subcommand.

Agent-agnostic

Materialises symlinks where each agent expects to read skills (.claude/skills/, .agents/skills/). Adding a new agent is a one-line change.

How it works

A skill is a git ref, not a folder.

Every skill lives at refs/skills/<name>, and each tagged release at refs/skill-tags/<name>/vX.Y.Z. Skills travel with the repo's regular git push / git fetch machinery — git-skill never invents a transport.

If an upstream maintainer force-moves v1.0.0 to a different commit, every machine that already ran sync stays on the SHA in its lockfile. You opt into the new version explicitly with git skill get …@1.0.1.

Quick start

Three commands to a versioned skill.

1 Install

Grab the binary for your OS from releases, or build from source with go install.

# build from source
go install github.com/niradler/git-skill/cmd/git-skill@latest
2 Author

Scaffold a skill, edit SKILL.md, snapshot it, tag a release, publish to your remote.

git skill init code-review "PR checklist"
# edit code-review/SKILL.md
git skill commit code-review -m "Add checklist"
git skill tag code-review 1.0.0
git skill push origin
3 Consume

Anywhere else, install pinned by tag, commit skill.lock, teammates run sync.

git skill get \
  https://github.com/you/skills.git \
  code-review@1.0.0 \
  .claude/skills/
git add skill.lock && git commit -m "pin"
Usage

Common workflows.

Bump a skill across your team

Author tags 1.1.0; every consumer changes one line and commits the lock.

# author
git skill commit code-review -m "Add async-fn check"
git skill tag code-review 1.1.0
git skill push origin

# consumer
git skill get URL code-review@1.1.0 .claude/skills/
git add skill.lock && git commit -m "bump code-review to v1.1.0"
Reproduce a teammate's setup

They committed skill.lock; you just sync. No tags involved — the SHA is what binds.

git clone <their-app-repo>
cd <their-app-repo>
git skill sync
# fetching code-review from URL...
# synced code-review → .claude/skills/code-review (abc1234)
Revert to a previous version

Bad release just shipped? Re-install the old tag, commit the lockfile.

git skill get URL code-review@1.0.0 .claude/skills/
git add skill.lock && git commit -m "revert code-review to v1.0.0"
Inspect what changed between releases

Plain git diff — no special tooling needed.

git skill diff code-review v1.0.0 v1.1.0
# or with raw git:
git diff refs/skill-tags/code-review/v1.0.0 \
         refs/skill-tags/code-review/v1.1.0
Use with private repos

git-skill shells out to plain git fetch / push. Whatever credentials work for git clone work here.

# once per machine
gh auth login

git skill get \
  https://github.com/acme/private-skills.git \
  internal-rubric@2.0.0 \
  .claude/skills/
Use without the CLI

Skills are plain git refs — any git-aware tool reads them natively.

git cat-file -p refs/skills/code-review
# tree abc...
# author Your Name <you@example.com>
# Skill-Version: 1.0.0

git ls-tree refs/skills/code-review
# 100644 blob ...  SKILL.md
Best practices

How to use git-skill well.

DO Always commit skill.lock

It's the reproducibility contract. Without it, git skill sync is a no-op for everyone else. Commit it alongside the code change that consumes the skill.

DO Tag every published version

Tags are how consumers talk about "version 1.0.0". Untagged commits are still installable by SHA, but tags give your team something human-readable to reason about.

DO Treat skills like packages, not configs

Semver them. Write a short changelog inside SKILL.md for each release. Bumping a tag without notes is the fastest way to lose your team's trust.

DO Use a URL for remote

The remote field in skill.lock must resolve from every teammate's machine. https://github.com/… or git@github.com:… — never a local filesystem path.

DO Review third-party skills before installing

A SKILL.md is read by your agent the same way your instructions are. git skill diff the new tag before upgrading; treat it like a code review.

DON'T Move tags after publishing

Tags are technically mutable but treat them as immutable. Need to fix a bug? Cut a new patch version. Force-moving a tag breaks everyone's intuition about what v1.0.0 means.

DON'T Edit installed skill files in place

Files in .claude/skills/<name> are a materialised copy of an upstream commit. The next sync overwrites them. Fork the skill or open a PR upstream instead.

DON'T Mix skill commits with app commits

refs/skills/* are isolated from your app's main. Don't try to consolidate by cherry-picking between them — the disjoint history is a feature, not an accident.
